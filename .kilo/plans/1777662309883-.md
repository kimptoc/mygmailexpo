## PR Summary

Adds an Archive button to two surfaces in a Gmail Expo app:
- **`components/InboxScreen.tsx`**: selection-mode header shows `[Archive][Move]` in INBOX, `[Remove label][Move]` in user labels, `[Move]` only in system folders.
- **`app/email/[id].tsx`**: email detail header gains Archive when opened from INBOX.

Archive is implemented as `removeLabelIds: ['INBOX']` via the existing `removeLabelFromEmails`. A new utility `utils/folder-actions.ts` centralises the folder-type logic and is unit-tested. All 60 tests pass, TypeScript is clean, lint is clean.

## Concerns

### 1. Behavioral change when `currentFolder`/`folderId` is null (medium risk)

**`InboxScreen.tsx` — `handleRemoveLabelBatch`**

Before:
```ts
if (!currentFolder) return;  // early-exit, no-op
const sourceFolderId = currentFolder.id;
```

After:
```ts
// guard removed
const sourceFolderId = currentFolder?.id ?? 'INBOX';
```

And `selectionAction`:
```ts
// before
const showRemoveLabel = !!currentFolder && currentFolder.id !== 'INBOX' && ...
// → false when currentFolder is null → no button shown

// after
const selectionAction = getSelectionAction(currentFolder?.id ?? 'INBOX');
// → 'archive' when currentFolder is null → Archive button IS shown
```

The null-folder state was previously a "show nothing, do nothing" condition. It's now implicitly treated as INBOX. This is **probably correct** (no folder → shows inbox), but it's an undocumented assumption. If the screen can ever render without `currentFolder` set in a non-INBOX context, the button would appear and the action would archive against INBOX in error.

Same pattern applies in `app/email/[id].tsx` — `folderId` being `undefined` now shows an Archive button and archives from INBOX instead of being a no-op.

**Recommendation**: Add a comment documenting the `?? 'INBOX'` fallback intent, or assert that `currentFolder` is always set when selection mode is active.

### 4. `BatchErrorModal` action label not updated for archive (low severity)

In `handleRemoveLabelBatch`, when a batch operation partially fails, the existing `batchErrorDetails.action: 'remove'` is set. When archiving from INBOX, the error modal likely still uses "remove" wording. The spec explicitly calls this out as intentional (archive is a remove-label internally), but users who see the error modal while archiving could find the wording confusing.

---

### 5. The `{...{ title: "..." } as any}` pattern (low severity, pre-existing)

In `app/email/[id].tsx`, new buttons use:
```tsx
{...{ title: "Archive" } as any}
```
This is an existing pattern in the file, not introduced by this PR. The `as any` bypasses TypeScript type checking to pass a `title` prop that RN's `TouchableOpacity` doesn't officially type. Not a blocker, but worth flagging as tech debt.

---

### 6. Arrow function wrapper on `handleRemoveLabelBatch` is a fix (positive)

The old code called `handleRemoveLabelBatch` directly as `onPress`:
```tsx
<TouchableOpacity onPress={handleRemoveLabelBatch}>
```
This would pass the native `SyntheticEvent` as `idsToProcess`. The function happened to work because `Array.isArray(event)` is false and it fell back to `selectedIds`. The new wrapper:
```tsx
onPress={() => handleRemoveLabelBatch()}
```
is correct and intentional. This is an implicit bug fix.
